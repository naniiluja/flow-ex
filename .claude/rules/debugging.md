# Debugging (disciplined, no rushing)

Mandatory process when investigating a bug, followed directly in conversation (no separate debug command):

1. **Reproduce** — reconstruct the bug from symptom/input/environment before touching code.
2. **Trace step by step** — follow `runId`/`projectId` across `projects/<id>/logs/run-*.ndjson`, read entry+exit at each boundary.
3. **Inspect `project.json` read-only** (no DB in this project) — verify the scene/run state step by step.
4. **Isolate with evidence** — narrow the suspect area with file:line/log line/`project.json` field, not gut feeling.
5. **Failing test** — write a test reproducing the bug (red) first.
6. **Minimal fix** — fix only within scope, no side refactor.

> Never guess and fix on the spot before you have evidence.

- **Task 002, `renderVideo` crashed under real `node` but not under Vitest** — symptom: `node -e "import('./src/render/render-video.ts')"` threw `ERR_UNKNOWN_FILE_EXTENSION` for `.tsx`, while `vitest run` stayed green. Root cause: `render-video.ts` imported `MAIN_COMPOSITION_ID` as a VALUE from the `@flow-ex/video` barrel (`video/src/index.ts`), whose re-export chain resolved back to `root.tsx`; Node's native type-stripping (`tech-stack.md`) cannot load a `.tsx` file, but Vitest transforms it anyway, so the test suite could not see the break. Prevention: never import a runtime VALUE (only `import type`) from a barrel unless every file in that barrel's re-export chain is a plain `.ts`; a runtime constant that a JSX-bearing package needs to expose to a Node-type-stripped package belongs in its own plain `.ts` file (`video/src/composition-id.ts`), imported by deep path. Files: `be/src/render/render-video.ts:12`, `video/src/composition-id.ts`.
- **Task 002, transition pixel-sample assertion checked the wrong frame** — symptom: `render-video.test.ts`'s "not fully black during the transition" assertion passed even on a build that (hypothetically) rendered the transition fully black, because `/ccf:check` pass 3 proved the sampled timestamp (`firstJoinContentFrame - transitionFrames/2`) landed 12 frames BEFORE the transition window even started. Root cause: guessed the sign of the offset instead of deriving it from `TransitionSeries`'s real behavior, which starts the next sequence's transition `transitionFrames` frames BEFORE the previous sequence's own `durationInFrames` ends (so the true window is `[firstJoinContentFrame, firstJoinContentFrame + transitionFrames)`, not centered before it). Prevention: when a test samples a specific timing window, derive the window's bounds from the same frame arithmetic the runtime composition uses, and sanity-check by sampling a small scan of nearby frames once (not just the single assertion point) before trusting the number. Files: `be/src/render/render-video.test.ts:174-184`.
- **Task 003, every pipeline log line was written at pino level `info`, including errors** — symptom: `pipeline-engine.ts`'s `logAndEmit(level, fields, msg)` accepted a `level` parameter but its body called `.info(fields, msg)` unconditionally; `LOG_LEVEL=warn` in production would have silently swallowed every `pipeline.scene.*.error`/`pipeline.run.error` line. No test caught it because the NDJSON entry's own `level` FIELD is set directly from the parameter (`{ level, ... }`), independent of which pino method actually got called — a test reading the log file back still saw the "correct" level string. Root cause: copy-pasted a single `.info(...)` call across the file's original draft instead of dispatching on the parameter. Prevention: when a log helper takes a `level` argument, dispatch the ACTUAL logger call dynamically (`logger[level](...)`) and add a regression test that spies on the logger object itself (not just the persisted log entry) to assert the right method was invoked. Files: `be/src/pipeline/pipeline-engine.ts:88`, regression test `be/src/pipeline/pipeline-engine.test.ts` ("logs a scene failure at pino's error level, not info").
- **Task 003, a resumed-looking run could silently reuse a finished run's `runId`** — symptom: `project.runId ?? randomUUID()` only checked whether `runId` was ABSENT, not whether the project's PREVIOUS run had actually finished. Triggering `POST /api/projects/:id/render` twice on the same completed project would reuse the old `runId`, appending new log lines and SSE events under a run that had already been reported "completed" — defeating `logging.md`'s "grep the full trace of a run using only the run ID" goal. Root cause: treated "does an id exist" as equivalent to "is this a genuine resume", when only `runStatus === "running"` (a crash left it there) means the SAME run is continuing. Prevention: when a persisted identifier is meant to be reused ONLY across a crash-resume, gate the reuse on the STATE that a crash actually leaves behind, not merely on the field being non-null. Files: `be/src/pipeline/pipeline-engine.ts:67-68`.
