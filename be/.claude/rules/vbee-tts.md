# Vbee TTS (`VbeeTtsProvider`)

Contract from the user-provided Vbee docs, cross-checked against a real API call on 2026-09-16 (one
35-character request, `hn_female_ngochuyen_full_48k-fhg` voice). Only the **async batch** mode is used;
the realtime sync mode (`mode: "sync"`, ≤300 chars, 5 voices) is intentionally not implemented — its
limits don't fit every scene and a second code path would double the test surface for no gain.

## Endpoints

- **Submit:** `POST https://api.vbee.vn/v1/tts`, headers `Authorization: Bearer <token>`, `App-Id: <app-id>`, `Content-Type: application/json`.
  - Required body: `text` (trimmed, non-empty, ≤100,000 chars), `mode: "async"`, `webhookUrl`, `voiceCode`.
  - Optional body: `outputFormat` (`mp3`|`wav`, default `mp3`; `pcm` errors), `bitrate` ∈ {8,16,32,64,128} (default 128), `speed` 0.25–1.9 (default 1.0), `sampleRate` ∈ {8000,16000,22050,24000,32000,44100,48000}, `emphasisIntensity` 0–100 in steps of 10, `clientPause { majorBreak 0.1–10 (0.3), mediumBreak 0.1–10 (0.25), paragraphBreak 0–10 (0.6), sentenceBreak 0.1–10 (0.45) }`.
  - **Verified live:** success returns HTTP **201** (not 200) `{ requestId, status: "PROCESSING" }`. `webhookUrl: "https://vbee-callback.invalid/noop"` was accepted (`.invalid` never resolves per RFC 2606, so nothing leaks to a third party — this app runs on localhost and never receives the webhook).
- **Poll:** `GET https://api.vbee.vn/v1/tts/requests/{requestId}` (same headers) → `{requestId, status:"PROCESSING"}` or `{requestId, status:"COMPLETED", audioLink}`. **Verified live:** an unknown/expired id returns `400 {"error":{"code":"BAD_REQUEST","message":"Request is not found"}}`.
- **`audioLink` expires 3 minutes after it's issued**; the underlying audio is kept on Vbee for 3 days. Getting a fresh link means calling `GET` again — never re-`POST`.
- **Verified live:** the link is `https://vbee.vn/s/<requestId>/<id>`, which **302**s to an S3 presigned URL (`vbee-studio2-3.s3.ap-southeast-1.amazonaws.com`, query has `X-Amz-*` params); each `GET` returns a different presigned link, so the client must follow the redirect immediately rather than caching the URL.
- **Verified live:** the downloaded file's `Content-Type` is `application/octet-stream` regardless of `outputFormat` — validate the file by magic bytes (MP3 ID3v2 header), never by `Content-Type`. The test call returned MP3 ID3v2.4, 128kbps, 44.1kHz mono, 2.53s, and was `COMPLETED` on the very first `GET`.
- **Verified live:** wrong/missing auth returns **HTTP 401 with an HTML body from nginx**, not JSON — the provider must branch on status code alone for 401, never assume a JSON body.
- Callback payload (snake_case `request_id`/`status`/`audio_link`) is documented but unused, since this app has no public endpoint to receive it.

## Error codes

- `401 UNAUTHORIZED` (HTML body, see above) → `errorKind: 'needs_user'`.
- `400 BAD_REQUEST` where the message concerns insufficient credit → `errorKind: 'needs_user'`; any other `400` (bad `voiceCode`, unsupported `sampleRate`, malformed body) → `errorKind: 'fatal'` for that scene.
- `429 TTS_CCR_MAX_LIMIT_REACHED`, `500 TTS_SPEND_CREDITS_FAILED`, `500 INTERNAL_SERVER_ERROR`, network errors, request timeouts, and a non-JSON body on any status other than 401 → `errorKind: 'transient'`, follow the shared retry schedule in `../../../.claude/rules/error-handling.md`.

## Provider design

- Env: `VBEE_APP_ID`, `VBEE_TOKEN` (JWT, observed to carry only `iat`, no `exp` — it does not self-expire; never write either value into any file in this repo), `VBEE_WEBHOOK_URL` (default `https://vbee-callback.invalid/noop`). `be/src/server.ts` only builds real `vbeeCredentials` when BOTH `VBEE_APP_ID` and `VBEE_TOKEN` are set; otherwise `be/src/routes/render.ts`'s `selectTtsProvider` falls back to `FakeTtsProvider` (task 003), so local dev and the e2e test suite work without real credentials.
- The scene JSON's optional `tts: { speed?, bitrate?, sampleRate?, emphasisIntensity?, clientPause? }` block applies project-wide (`@flow-ex/shared-schemas`'s `ttsOptionsSchema`, reused as-is here rather than redefined); zod validates it against the exact domains above (this is the EP/BVA matrix subject for this provider).
- **Task 009:** an unset `tts.speed` no longer always falls back to Vbee's own default of `1.0` — `be/src/routes/render.ts` calls `resolveTtsOptionsForProject(project.preset, project.tts)` (`be/src/providers/select-providers.ts`) before constructing the provider, which fills a missing `speed` from `PRESETS[project.preset].ttsSpeed` (`1.15` for `tiktok`, `1.0` for `youtube`, `@flow-ex/shared-schemas/src/presets.ts`) — an EXPLICIT `tts.speed` still wins over the preset (../../.claude/rules/video.md's "aspectRatio vs preset" decision applies the same rule here).
- Per-scene state in `project.json` is FLAT on the scene object (not nested under an `audio` key, matching `imageFile`/`imageWidth` etc.'s own convention): `audioRequestId`, `audioRequestSubmittedAt`, plus the generic `status`/`attempts`/`lastError`/`audioFile`/`audioDurationMs` fields `pipeline-engine.ts` already manages for every provider. `VbeeTtsProvider` itself never touches `project.json`; it calls `AudioGenerationContext.onRequestSubmitted({requestId, submittedAt})` the moment `POST` returns 201, and the pipeline engine persists it atomically (`be/src/pipeline/pipeline-engine.ts`'s `runAudioStep`) BEFORE polling starts, so a crash mid-poll can resume from it.
- Resume logic on restart: audio file already on disk → `runAudioStep` never re-enters this step (already `ready_for_render`); `AudioGenerationContext.existingRequest` present and under 3 days old → only `GET`, never re-`POST`; absent, or `"Request is not found"` from a poll, or 3+ days old → submit a fresh `POST` (logs `vbee.request.resubmit` instead of `vbee.request.submit` specifically for this "had one, it went stale/missing" case).
- Polling: 2s for the first attempt, 5s for every attempt after that, for up to 5 minutes total (`pollTimeoutMs`, injectable for tests); exceeding that throws `VBEE_POLL_TIMEOUT` (`errorKind: transient`), which the OUTER `retryWithSchedule` in `pipeline-engine.ts` then retries per the shared 30s/2m/5m schedule — polling "still processing" is never itself a retryable error, only a real HTTP failure or the overall timeout is.
- On `COMPLETED`: `fetch` follows the redirect automatically, verify MP3 magic bytes (`ID3` prefix) before trusting the bytes, then write directly into `assets/audio/<sceneIndex>.mp3` (`fs.writeFile`, no separate temp-file rename step — the pipeline's own atomic `project.json` write is what protects against a half-finished RUN, and a half-written audio file left behind by a kill mid-write is simply overwritten by the resumed run's own retry of this same step, since `runAudioStep` only advances past `generating_audio` after the file+duration are both persisted). A 403/404/other non-2xx on the audioLink itself (expired) triggers one fresh `GET` for a new link via `pollOnce`, retried at most 2 times (`MAX_EXPIRED_LINK_RETRIES`) before surfacing the download error as `transient`.
- **Concurrency (task 014-audio, 2026-09-18, superseding the earlier "NONE needed" note): audio now runs CONCURRENTLY across scenes**, mirroring the image phase's own task-014 design. `pipeline-engine.ts`'s phase 2 runs `runAudioStep` through a `p-queue` (`VBEE_AUDIO_CONCURRENCY`, default 3) instead of the old sequential `for` loop — a real 26-scene render (`WHISPER_MODEL=medium`, `VBEE_AUDIO_CONCURRENCY` default) confirmed multiple scenes' `generating_audio` steps genuinely overlap. Unlike Flow's image phase, there is no shared browser page to serialize a submission around: each `synthesize` call is an independent HTTP request, so no `SubmitMutex`-equivalent exists here, and a failure in one scene never lowers the queue's concurrency (unlike the image phase's failure-triggered step-down) — Vbee's own 429 handling in the retry schedule already bounds runaway concurrent load. `VbeeTtsProvider` itself required ONE fix for this: `runAudioStep`'s `existingRequest` lookup used to read the pipeline's shared outer `project` variable, which under concurrency can be a stale snapshot from before this exact scene's own state committed; it now reads fresh from the store on every attempt (`backend-conventions.md`'s task-014 invariant). Captions (phase 3, whisper.cpp) remain SEQUENTIAL — a local CPU-bound process gains nothing from parallel instances contending for the same cores, unlike Vbee's independent network calls.
- `durationMs` is measured from the REAL downloaded file via ffprobe (`be/src/providers/vbee/measure-audio-duration.ts`, `@ffprobe-installer/ffprobe` — a `dependencies` entry, not `devDependencies`, since this runtime code path uses it, unlike task 002's own test-only use of the same package), never trusted from Vbee's response (which doesn't return a duration at all).
- Logging (`../../.claude/rules/logging.md` "each cross-boundary call logs both entry and exit", plus the required `projectId`/`runId`/`sceneIndex`/`stage` correlation fields): `vbee.request.submit`/`.success`/`.error`, `vbee.request.resubmit`/`.success`/`.error` (the "had a stale/missing request" case), `vbee.audio.download`/`.success`/`.error`. `AudioGenerationContext.logger` (`be/src/domain/providers.ts`) carries a per-run child logger (`{projectId, runId, stage: "audio"}`) that `pipeline-engine.ts`'s `runAudioStep` builds fresh on every `synthesize` call, since the provider is constructed before `runId` exists; `VbeeTtsProvider` prefers this over its own construction-time `options.logger`, so these pino lines carry the same `runId`/`stage` correlation fields as the rest of the run. This is pino output only: neither this logger nor `pipeline-engine.ts`'s own `logAndEmit` routes a `VbeeTtsProvider` line into `logs/run-<runId>.ndjson` or the SSE `log` stream — only the pipeline's own `pipeline.scene.audio.*` lines reach those (`../../../.claude/rules/logging.md`'s "Known gap"). The repeated poll-while-PROCESSING call is deliberately NOT logged per attempt (every 2-5s for up to 5 minutes would flood the log for no diagnostic gain); the overall audio-step outcome is already covered by `pipeline-engine.ts`'s generic `pipeline.scene.audio.success`/`.error`.
- Secrets never reach a log line in the first place, which is a stronger guarantee than relying on `redact` alone (`../../../.claude/rules/logging.md`): no `AppError` this provider throws ever puts `authorization`, `app-id`, `VBEE_TOKEN`, the raw `audioLink` URL, or its `X-Amz-*` query params into its `message`/`context` — every error message that mentions "audioLink" uses the literal word, never the interpolated URL value. Pino's root `redact` list (`authorization`, `app-id`, `VBEE_TOKEN`, `audioLink`) remains the defense-in-depth backstop for any future code path that does log one of these directly.
