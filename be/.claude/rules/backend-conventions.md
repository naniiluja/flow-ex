# Backend Conventions

## Structure

- Folder organization: `be/src/routes/` (Fastify handlers) → `be/src/pipeline/` (state machine, retry, orchestration) → `be/src/domain/` (types, `AppError`, provider interfaces) ← `be/src/providers/{flow,vbee}/` (concrete providers) and `be/src/store/` (project persistence).
- Dependency injection: plain constructor/factory parameters (e.g. `createPipeline({ imageProvider, ttsProvider, store, logger })`), no DI container/framework.

## Verifiable rules

- Thin handlers, logic in service/pipeline.
- Config via env vars (`VBEE_APP_ID`, `VBEE_TOKEN`, `VBEE_WEBHOOK_URL`, `PORT`, `CHROME_USER_DATA_DIR`, `CHROME_CDP_PORT` (default `9222`), `CHROME_EXECUTABLE_PATH` (optional override, default: standard macOS Chrome.app path), `FLOW_IMAGE_PROVIDER` (`"fake"`|`"real"`, default `"fake"` — task 005's explicit opt-in switch, since Chrome connection settings always have a default and can't by themselves signal "use the real provider" the way Vbee's credentials do), `FLOW_IMAGE_CONCURRENCY` (default `3`, task 014 — the STARTING ceiling for how many scenes' image steps `pipeline-engine.ts` runs concurrently against the shared Flow page; the engine itself lowers this toward 1 at runtime on repeated consecutive failures), `TRANSCRIBE_PROVIDER` (`"fake"`|`"whisper"`, default `"fake"` — task 007's own explicit opt-in switch, same rationale), `WHISPER_MODEL` (default `"small"`, always a MULTILINGUAL model per `../../.claude/rules/video.md`, never a `.en` one), `WHISPER_CPP_VERSION` (default `"1.5.5"`), `WHISPER_CACHE_DIR` (default `"./.whisper-cache"`, where the whisper.cpp binary + downloaded model are cached ONCE per process — shared across every project, unlike `projects/<id>/assets/`), `LOG_LEVEL`, `NODE_ENV`; `PROJECTS_DIR` is an internal override for tests/local runs only, not user-facing), validated once at startup with a zod schema (`be/src/env.ts`); never hardcode secrets: a committed secret outlives its own rotation and leaks through every clone/fork of the repo.
- **Task 014 — no step can assume the pipeline still processes one scene at a time.** `pipeline-engine.ts`'s image phase runs multiple scenes' image steps CONCURRENTLY (see `flow-automation.md`'s "Tile identity"); a step that runs during this phase must read whatever scene/project state it needs from INSIDE its own `ProjectStore.update()` callback (or from that call's own local return value / a fresh `store.read()`), never from a shared outer variable a DIFFERENT scene's concurrently-running task can reassign between two `await`s. `pipeline-engine.ts`'s `executeStep`/`runImageStep` are the reference implementation of this pattern; `runAudioStep`/`runCaptionStep` still run sequentially (per-scene, after the WHOLE image phase completes) but were updated to the same pattern defensively. Any comment elsewhere in this codebase still claiming a provider or pipeline step is "safe because scenes are processed one at a time" is now WRONG for the image phase specifically — `vbee-tts.md`'s equivalent claim about `VbeeTtsProvider` remains true, since the audio phase itself is still sequential.
- Every endpoint has a test (per `../.claude/rules/testing.md`).
- Graceful shutdown: catch `SIGINT`/`SIGTERM` and call `fastify.close()` before exit, so an in-flight write finishes instead of corrupting `project.json`. On close, branch on success/failure (`app.close().then(onOk, onError)`); never `void`/`.finally()`-swallow a rejected close, which would exit 0 on a failed shutdown.
- Only wrap a route plugin in `fastify-plugin` (`fp()`) when it must leak a decorator/hook to the PARENT scope. A plain route-registration plugin (like `be/src/routes/projects.ts`) should stay encapsulated and export the bare `FastifyPluginCallback`/`FastifyPluginAsync` function; `fp()` there breaks encapsulation for no benefit.
- `AppError`'s HTTP status comes from an explicit `code → status` table in `be/src/app.ts` (`STATUS_BY_APP_ERROR_CODE`) plus an `errorKind` fallback, never a chained ternary — a new error code should only need a table entry when it needs a non-default status.
